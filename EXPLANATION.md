This document provides a deep-dive explanation of the DevOS codebase, architectural patterns, state machines, and implementation details for developers.

## 1. Database Layer (PostgreSQL + pgvector + Prisma)

### Table Schema Structure
We utilize a relational PostgreSQL database managed via **Prisma 6**. The database holds 14 tables (13 base tables + the `WebhookEvent` idempotency cache table):
- `User`: Manages user records, profile details, and authentication relationships.
- `Organization`: The multi-tenant boundary. Everything (members, repositories, sprints) filters by `orgId`.
- `Membership`: A join table linking `User` and `Organization` with specific role boundaries (`OWNER`, `ADMIN`, `MEMBER`).
- `Repository`: Links imported GitHub repos to organizations.
- `Commit`, `PullRequest`, `Issue`: Relational models mapped to imported GitHub entities.
- `Sprint`, `Task`: The Kanban core models. Tasks belong to a status column (`BACKLOG`, `TODO`, `IN_PROGRESS`, `IN_REVIEW`, `DONE`) and can optionally link to a sprint, assignee, or GitHub issue.
- `WebhookEvent`: Logs GitHub delivery IDs to check for duplicates.
- `AuditLog`, `Notification`, `AiReview`: Analytics, notification broadcasts, and PR scorecards.
- `AiDocument`: Codebase document blocks containing vector embeddings.

### pgvector Support
In `backend/prisma/schema.prisma`, we define:
```prisma
model AiDocument {
  id        String   @id @default(uuid())
  content   String
  metadata  Json?
  embedding Unsupported("vector(1536)")?
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```
During the initial migration bootstrap, we prepended the raw SQL commands:
```sql
CREATE EXTENSION IF NOT EXISTS vector;
```
This registers the pgvector extension, allowing us to store high-dimensional semantic code chunks (1536 floating-point values generated by OpenAI `text-embedding-3-small`) and execute cosine similarity operations directly in database queries.

## 2. Authentication & Multi-Tenant Role Access Control (RBAC)

### JwtStrategy
The backend extracts authorization headers using passport JWT strategies. If the JWT token signature and expiry check pass, it queries the database and attaches the full user entity to the request context:
```typescript
// Attached to req.user
request.user = { id: '...', email: '...', name: '...' }
```

### RolesGuard & Scope Resolution
To protect organization resources, we use a custom `@Roles` decorator combined with a path-aware `RolesGuard`:
1. **Scope Parsing**: The guard dynamically inspects the request parameters (checking for `:orgId` or `:id` placeholders in URLs).
2. **Membership Check**: It queries the `Membership` join table matching the organization ID and the authenticated user's ID (`req.user.id`).
3. **Role Validation**: If the user's role satisfies the `@Roles` requirements (e.g. `OWNER` or `ADMIN`), the request is permitted; otherwise, it throws a `403 Forbidden` exception.

```typescript
@Controller('orgs/:orgId/repositories')
@UseGuards(JwtAuthGuard, RolesGuard)
export class RepositoriesController {
  @Post('import')
  @Roles(Role.OWNER, Role.ADMIN) // Enforces OWNER/ADMIN roles
  async importRepo(...) { ... }
}
```

## 3. Asynchronous Task Processor (Redis + BullMQ)

Heavy operations like repository imports are processed out-of-band to prevent API gateway timeouts:

```
[API Gateway] ──> Enqueues Job ──> [Redis Queue] ──> [SyncProcessor Worker] ──> DB Updates
```

1. **Job Enqueueing**: The `SyncQueue` service adds jobs to the `github-sync` queue, storing parameters (`repoId`, `orgId`) in Redis.
2. **Job Processing**: The `SyncProcessor` worker runs as an independent daemon. It intercepts jobs, reads the repository details, pulls data from the GitHub Octokit wrapper, and inserts the records into the database.
3. **Config resilience**: If the job fails (e.g. GitHub rate limits), it utilizes exponential backoff policies to retry execution 3 times.

## 4. Webhook Verification & Idempotency Pipeline

```
GitHub Webhook ──> Raw Body Extraction ──> Signature Verification ──> Idempotency Check ──> Processing
```

1. **Raw Body Capturing**: In `main.ts`, we bootstrap NestJS with `{ rawBody: true }`. This mounts the raw request buffer to `req.rawBody` before JSON parsing.
2. **HMAC Signature Check**: We extract `x-hub-signature-256` and compute:
   ```typescript
   const hmac = crypto.createHmac('sha256', secret);
   const digest = 'sha256=' + hmac.update(req.rawBody).digest('hex');
   ```
   We verify this against the header using `crypto.timingSafeEqual()` to protect against timing attacks.
3. **Idempotency Check**: We extract the `x-github-delivery` header. We query the `WebhookEvent` table. If the ID is found, we ignore the request and return `200 OK` immediately. Otherwise, we write the event log as `PENDING` and continue.

## 5. File Storage Strategy Pattern

To keep files decoupled from cloud configurations, we use the **Strategy Pattern**:
- **Interface**: `IStorageProvider` defines `uploadFile()`, `deleteFile()`, and `getFileUrl()`.
- **LocalStorageProvider**: Saves files to a local uploads directory in the current working path. Useful for offline, local runs.
- **S3StorageProvider**: Interfaces with Amazon S3 using the `@aws-sdk/client-s3` client.
- **Resolver**: Based on the `STORAGE_PROVIDER` environment variable (`local` vs `s3`), the `StorageService` dynamically injects the appropriate driver.

## 6. Next.js 15 Frontend Framework Details

### Zustand Session Store
We manage active login profiles and session tokens in a Zustand store. We use the `persist` middleware to sync state into `localStorage` so sessions persist across browser tab refreshes:
```typescript
export const useAuthStore = create<AuthState>()(
  persist(
    (set) => ({
      user: null,
      accessToken: null,
      refreshToken: null,
      ...
    }),
    { name: 'devos-auth-storage' }
  )
);
```

### Axios Auto-Refresh Token Interceptor
Our custom Axios client [api.ts](file:///Users/ganeshpirikirala/Desktop/Ai-platform/frontend/src/lib/api.ts) performs two crucial tasks:
1. **Request Interceptor**: Extracts the `accessToken` from the Zustand store and injects it into headers as `Authorization: Bearer <token>`.
2. **Response Interceptor**: If an HTTP request fails with a `401 Unauthorized` error:
   - It captures the failed request context.
   - It triggers a silent request to the NestJS backend `POST /auth/refresh` using the `refreshToken`.
   - If token rotation succeeds, it stores the new tokens in Zustand and retries the original request.
   - If token rotation fails (refresh token expired), it clears the session and logs the user out.

### Pages & Routing Structure
- `/register`: Credentials creation. Supports form validation and parses NestJS array error messages.
- `/login`: Password forms + GitHub OAuth redirection anchor (`http://localhost:3001/auth/github`).
- `/auth/callback`: Collects tokens from redirect parameters, updates Zustand, fetches profile metrics via `/auth/me`, and navigates to dashboard.
- `/dashboard`: Core dashboard displaying organizations switcher, team rosters, and organization creation forms.
